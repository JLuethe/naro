Issue #3: durable save, backup, and lock acceptance

Review the implementation as well as the harness.

- Safe atomic replacement must be the default. Any in-place compatibility mode
  must be explicitly selected and justified by repository evidence.
- The replacement must be written through a uniquely and exclusively created
  temporary file in the destination directory.
- Verify complete writes, short and partial writes, repeated EINTR, EIO, ENOSPC,
  file-sync failure, checked-close failure, rename failure, containing-directory
  sync failure, and deterministic interruption boundaries.
- Before the rename commit point, failure must leave the original pathname,
  bytes, inode, and required metadata unchanged. The destination pathname must
  not be replaced until new contents are fully written and file-synced.
- After replacement, directory-sync failure must report failure and must not
  mark the buffer saved, while accurately acknowledging that replacement may
  already have occurred.
- Verify safe identity-checked cleanup. A stale cleanup path must never remove a
  substituted or unrelated inode.
- Test regular existing and new files, overwrite, append, prepend, permissions,
  ownership, set-ID behavior, timestamps, ACLs/xattrs where supported, final
  symlinks, hard links, inode replacement, and temporary-name collisions.
- Verify and document the policy: final symlink refusal; hard-link splitting;
  inode replacement; and other deliberate differences from nano's in-place
  behavior.

Backup-specific regression requirements

- Exercise secure and INSECURE_BACKUP configuration, confined and unconfined
  operation, missing/regular/hard-link/symlink backup destinations, collisions,
  fallback, read errors, and every injected save/backup fault.
- A backup pathname that is a hard link or symlink to the source/destination
  must never be opened with truncation. Publication must use an exclusive sibling
  temporary, checked close, file sync, rename, and directory sync.
- Prove failures before backup publication preserve the previous backup pathname
  and contents. Verify post-publication failure reporting deliberately.
- Verify INSECURE_BACKUP is a documented compatibility option and does not
  re-enable alias truncation.

Lock-specific regression requirements

- Save-as to the buffer's remembered lock pathname must preserve the newly saved
  destination. Lock cleanup must compare retained ownership identity before
  unlinking.
- Test confined and unconfined save-as collision cases, saved/modified state,
  stat/name state, undo/redo state, and cleanup of a genuinely owned new lock.
- Test normal lock creation, refresh, explicit accepted takeover, conflict
  refusal, substituted-entry preservation, and a pre-existing new-sidecar entry.
- Only the explicit user-approved takeover path may remove an unowned lock.
  Ordinary creation, save-as, refresh, or cleanup must not do so.
- Verify lock creation failure after a successful save is reported without
  falsely turning the committed save into data loss.

Fault-injection and negative-control requirements

- Run the complete safe-save, backup, recovery, and lock regression suites for
  every applicable default/tiny profile.
- Prove each intended fault actually fired and each required assertion executed.
  A command returning zero without a fired marker or meaningful assertion is not
  coverage.
- Preserve clean negative-control evidence showing the relevant newly added
  regression fails against the immediate pre-fix revision and passes at
  CANDIDATE. Bind it to revision, test-source hash, binary hash, command, status,
  and log. Use only ordinary synthetic fixtures.
- In particular, retain negative controls for the fortified-open gate, backup
  alias truncation, and save-as/lock-path deletion.
- On glibc, prove interception of fortified __open_2, __open64_2, and __openat_2
  where present, preserving variadic mode arguments including O_TMPFILE.
- Verify the shared open-gate implementation is used by default and tiny CI
  checks. An inert FIFO must cause the gate to fail, not silently pass.
